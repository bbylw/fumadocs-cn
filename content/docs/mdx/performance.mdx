## 概览 [#overview]

Fumadocs MDX 是一个打包工具插件，换句话说，它的性能上限较高，实际瓶颈取决于底层的打包工具。

以 Turbopack 和 Vite 等常见的打包工具来说，它足以应付拥有将近 500+ 个 MDX 文件的大型文档网站，几乎能满足所有使用情境。

由于 Fumadocs MDX 与你的打包工具搭配运作，你可以在 MDX 文件中导入任何文件，包括客户端组件。
这带来了极高的弹性，并确保所有内容默认都经过优化。

### 开发服务器 [#development-server]

分为两种类型：

* **Lazy**：Vite 等打包工具，以及 Node.js 和 Bun 等运行时端的加载器，可以在请求模块时 (例如调用 `await import()` 时) 按需编译 MDX 文件，因此开发服务器的性能不太会受到 MDX 文件数量影响。

  不过，请务必激活[延迟加载](/docs/mdx/async)，延迟编译才会生效。

* **Precompiled**：Webpack 和 Turbopack 在开发模式下不支持延迟编译，所有 MDX 文件都必须事先编译。按需预先编译的 MDX 文件数量而定，开发服务器可能会变慢。

  虽然这是打包工具层级的限制，但如果你在意速度问题，我们建议改用[本地 Markdown](/docs/integrations/content/local-md)。它会略过打包工具层，在运行时加载并编译 MDX 文件。详情请参阅链接中的介绍。

### 图片优化 [#image-optimization]

Fumadocs MDX 会通过 [Remark Image](/docs/headless/mdx/remark-image) 将图片解析为静态导入。
因此，图片会依你所使用的 React 框架自动进行优化 (例如 Next.js Image API) 。

```mdx
![Hello](./hello.png)

或放在 public 文件夹中

![Hello](/hello.png)
```

输出结果：

```mdx
import HelloImage from './hello.png';

<img alt="Hello" src={HelloImage} />
```

### 正式环境构建 [#production-build]

在正式环境构建中，最耗时的部分通常是 TypeScript docgen (没有 tsgo 时，TypeScript 编译器相当缓慢) ，以及所有 MDX 文件各自零碎的处理工作累加起来的开销。

在没有缓存的情况下，大量 MDX 文件可能会在构建期间造成极高的内存用量，原因如下：

* MDX 文件编译成 JavaScript 之后，打包工具还得再打包输出的 JavaScript 文件。
* 即使单一 MDX 文件的编译时间微不足道，累加起来仍可能相当可观。例如约 2500 个文件，假设每个文件需要 25ms，冷构建最多将耗时 62.5 秒。

主要的解决方式是改为随需编译，让内容只在收到请求时才加载。

#### 本地 Markdown [#local-markdown]

如开发服务器一节所建议，[本地 Markdown](/docs/integrations/content/local-md) 是不错的替代方案：它完全在运行时运作，不需要额外的编译步骤。

#### 远程来源 [#remote-source]

创建自定义的内容来源，并以远程方式加载内容。

如果你的内容来源不需要预先编译内容文件，便可通过 SSG 依需求处理这些文件，进而**提升构建速度。**
不过，这样就无法运用构建时期的优化 (例如打包) 。

如需实现自定义来源，请参阅[自定义来源](/docs/integrations/content/custom)。
